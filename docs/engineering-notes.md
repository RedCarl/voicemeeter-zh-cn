# 逆向工程笔记：三条硬约束

这份笔记记录在实现过程中**用实验逼出来的**、违反就会崩溃或显示异常的约束。
如果你要改动 `src/build_mempatch.py` 或添加新条目，请先读完。

---

## 约束 1：只能写「自己的字节 + 紧跟的连续 NUL 填充」

`.rdata` 是只读页，但真正的坑不在权限，而在**能写多长**。

看起来最自然的做法是"从字符串起点一直清零到下一个字符串起点"。这是错的。

`.data` 段里存在**定长记录**，例如：

```
0x180170  'BUS A1' \0  <121 个 NUL>  <8 字节真实数据: 87 1E 00 00 00 00 00 00>
```

如果按"到下一个字符串起点"清零，那 8 字节真实数据就被抹掉了，
程序启动即崩溃（已复现）。

**正确做法**：可写范围 = 字面量自身字节 + 终止符 + **紧跟的连续 NUL 字节**，
并且以"下一个字面量起点"为上限。

对应 `src/peutil.py` 的 `Spans.safe_span()`。

---

## 约束 2：绝不写 `.data` 段的重复字面量

同一个字符串可能在 exe 里出现多次。其中一部分位于 `.data`，
是**被程序解析比对的数据表项**，例如 Potato 里 `0x180170` 起的
`BUS A1` … `BUS B5`、`Learn`、`16 bits` / `24 bits`。

翻译这些会崩溃（已复现）。

**正确做法**：只写 `.rdata` 中出现的字面量。构建器用 `PE.in_rdata()` 过滤，
并会报告"跳过 N 处在 .data 段的重复字面量"。

> 注意：唯一允许出现在 `.data` 的改动是**多行消息框**——那类字面量确实在
> `.rdata`，只是需要逐行等长处理（见约束 3）。

---

## 约束 3：多行消息框必须逐行等长

`MULTILINE` 里的长消息（多行提示框）在编译时被 MSVC 的**字符串池后缀合并**
（`/GF`）处理过：一个长字符串可能同时是多个更短字面量的"后缀"。

例如 `"A\nB\nC"` 的第 3 行 `C` 可能被别处单独引用。
如果翻译后某一行的字节数与原文不同，**后续行的偏移就会移动**，
那些后缀引用就全错位了。

**正确做法**：逐行翻译，每行用空格补齐到与原行**完全相同的字节数**，
换行符位置保持不动。构建器会逐行校验并在超长时跳过。

---

## 约束 4：译文还要过「显示宽度」这一关

字节数放得下 **≠** 显示放得下。

界面里有些标签区是**固定宽度**的，而**汉字字形宽度约为拉丁字母的 2 倍**。

实测：Banana 旋钮下的 `Gate`（宽 4）译成「噪声门」（宽 6）时，
**第三个字被控件裁掉**，屏幕上只显示出「噪声」加半个字；改成「噪声」（宽 4）后正常。

**正确做法**：用 `2 × 汉字数 + ASCII 数` 估算显示宽度，超过原文就告警。
构建器的 `--check` 会列出这些条目。

菜单项、提示文本的宽度是自适应的，不受影响；**固定宽度的标签**才需要注意。

当前已知安全的取舍：

| 原文 | 译文 | 说明 |
|---|---|---|
| `Gate` | `噪声` | 只能放 2 个汉字，「噪声门」会被裁 |
| `Comp.` | `压缩` | 放得下 |
| `Ok` | `Ok` | 只有 4 字节可用，放不下「确定」，保留英文 |
| `In #1` | `输入1` | 去掉空格，宽度正好对齐 |

## 约束 5：菜单项有一份「内嵌加速键」的独立字面量

这是最容易漏的一点。

同一个菜单项在 exe 里往往有**两份**字面量：

```
0x158218  'Restart Audio Engine'                ← 托盘菜单等使用
0x1582a0  'Restart Audio Engine\t[CTL+R]'       ← 弹出菜单使用（加速键内嵌）
```

只翻译前者的话，**弹出菜单仍然是英文**。

翻译时必须**保持 `\t` 之后的部分逐字节不变**，否则 `[CTRL+R]` 这类加速键会失效。

> 有意思的细节：字面量里写的是 `[CTL+R]`，而菜单实际显示 `[CTRL+R]`——
> 说明显示用的加速键文字是程序自己生成的，字面量里那段只是冗余。
> 无论如何，保持原样最安全。

## 附：字符串布局速查

| | Banana `voicemeeterpro_x64.exe` | Potato `voicemeeter8x64.exe` |
|---|---|---|
| 版本 | 2.1.3.0 | 3.1.3.0 |
| 大小 | 7,361,568 | 13,548,576 |
| 标准资源 | **无** `STRINGTABLE`、**无** `DIALOG` | 同 |
| 界面文字位置 | `.rdata` 0x162200–0x181C00 附近 | `.rdata` 0x152000–0x15F000 附近 |
| 编码 | **ANSI 与 UTF-16LE 混排** | 同 |
| 绘制方式 | `TextOutA` / `DrawTextA` / `DrawTextW` + `CreateFontIndirectA` | 同 |
| 活动代码页 | 936 → ANSI 侧直接写 GBK 字节即可 | 同 |
| 菜单 | exe 内 `MYMAINAPPMENU` 资源是**死代码**（未导入 `LoadMenu*`），菜单全部由运行时 `CreatePopupMenu` / `AppendMenuA` 构建 | 同 |
| 主窗口类名 | `VBCABLE0Voicemeeter0MainWindow0` | 同 |

字符串引用方式（三种并存）：

1. `.data` 里的 64 位绝对指针表
2. `movzx eax, word ptr [rcx + rdx + <RVA>]`，其中 `rdx` = 模块基址，位移里嵌了 32 位 RVA
3. RIP 相对 `lea` / `mov`（镜像基址 `0x140000000`）

## 约束 6：32 位构建是另一套布局，且 PEB 结构不同

VoiceMeeter 有四个主程序，**32 位和 64 位的字符串布局完全不同**，必须各自生成计划：

| 构建 | 可执行文件 | 条目 |
|---|---|---|
| Potato 64 位 | `voicemeeter8x64.exe` | 552 |
| Potato 32 位 | `voicemeeter8.exe` | 548 |
| Banana 64 位 | `voicemeeterpro_x64.exe` | 528 |
| Banana 32 位 | `voicemeeterpro.exe` | 524 |

开始菜单里不带 `(x64)` 字样的条目指向的是 **32 位**版 —— 这是"我打开软件还是英文"
最常见的原因。

两个容易踩的点：

1. **PE32 的 ImageBase 位置不同**：PE32 在 `opt+28`（DWORD），PE32+ 在 `opt+24`（QWORD）。
   按 64 位读 PE32 会得到垃圾值。
2. **PEB 里的 ImageBaseAddress 偏移不同**（启动器挂起后要靠它拿模块基址）：
   * 64 位目标：`PEB + 0x10`，8 字节
   * 32 位目标（WOW64）：先 `NtQueryInformationProcess(ProcessWow64Information=26)`
     拿到 32 位 PEB，再读其 `+0x08`，**4 字节**

另外 32 位构建的字符串**可用空间通常更小**。例如 `Mute BUS A1` 后面只剩 12 字节，
`总线 A1 静音`（13 字节）放不下，必须改成 `总线A1静音`（10 字节）才能让
一份译文同时适配两个构建。

## 附：怎么加一条新翻译

1. 在 `translations/zh_cn.py` 的 `TRANSLATIONS` 里加 `("英文原文", "中文译文")`。
   英文原文**必须与界面上的文字完全一致**（含空格、标点、`\t` 后的加速键段）。
2. 跑 `python src/build_mempatch.py --check`，看有没有告警。
3. 跑 `python src/build_mempatch.py` 重新生成计划。
4. 用 `启动汉化版VoiceMeeter.cmd` 启动，确认显示正常。

找不到某条文字时，可以用 `find_literal()` 的思路在 exe 里搜：

```python
from peutil import PE, find_literal
pe = PE(r"C:\Program Files (x86)\VB\Voicemeeter\voicemeeter8x64.exe")
for kind in ("A", "W"):
    for off in find_literal(pe.data, "你要找的文字", kind):
        print(kind, hex(off), pe.section_of(off))
```

如果只在 `.data` 里找到，那就**不要**翻译它（见约束 2）。
